# rosecod.es

Source for [rosecod.es](https://rosecod.es) — my personal site.

This started as a **static export** from [Sitejet](https://sitejet.io) (a drag-and-drop website builder), previously hosted through FastComet. FastComet dropped the hosting, so this repo exists to move the same site onto **GitHub Pages** and make it something that's actually pleasant to hand-edit going forward — no more Sitejet editor, no more opaque numeric ids, no more 500MB of duplicate images. This README is a full map of how it's put together now.

## Pages

Each route is a folder containing its own `index.html`, so clean URLs (`/projects`, not `/projects.html`) work automatically on any static host, including GitHub Pages:

| URL | File | What's there |
|---|---|---|
| `/` | `index.html` | Home |
| `/projects` | `projects/index.html` | Project write-ups, including links to [`fractum`](https://github.com/roserha/fractum), [`city-parallax`](https://github.com/roserha/city-parallax), and [`ocarina-listener`](https://github.com/roserha/ocarina-listener) |
| `/experience` | `experience/index.html` | Academic / technical experience |
| `/hobbies` | `hobbies/index.html` | "The fun activities I do" |
| `/legal-notice` | `legal-notice/index.html` | Legal notice |
| `/privacy` | `privacy/index.html` | Privacy policy |

`sitemap.xml` lists these same six URLs for search engines.

## Folder structure

```
├── index.html, projects/, experience/, hobbies/, legal-notice/, privacy/   → the pages above (source — see "Build system" below)
├── _includes/nav.html, _includes/footer.html   → the shared nav/footer, edited once, stitched into every page at build time
├── build.py                             → the entire build step. Reads the files above, writes the final site to _site/
├── .github/workflows/deploy.yml         → runs build.py and publishes _site/ to GitHub Pages on every push
├── .prettierrc.json                     → formatting config (see "Formatting" below) — always run pages through this, don't hand-format
├── css/custom.*.css, js/custom.*.js     → page-specific styles/scripts written in the Sitejet editor
├── webcard/                             → Sitejet's own runtime (menu, forms, animations, jQuery/slick carousel, self-hosted Font Awesome, lazy-loaded locale/theme chunks). Don't hand-edit; it's regenerated by the builder.
├── g/                                   → self-hosted Google Fonts (DM Serif Display, Inter, Lato, Open Sans, Montserrat, Raleway) + g/fonts.css, linked from every page
├── images/                              → every photo/video/PDF the site uses — flat, one file each, see below
├── CNAME                                → custom domain for GitHub Pages: rosecod.es
├── sitemap.xml
```

## Build system

The six page files are still where you'd expect them and are still what you edit directly — there's no separate "content" format to learn. The only thing that changed is the nav bar and footer: instead of being pasted into all four pages that use them (`index.html`, `projects/index.html`, `experience/index.html`, `hobbies/index.html`), each of those pages now has two one-line markers where that content goes:

```html
<!--#include nav active="projects"-->
...
<!--#include footer-->
```

`build.py` reads every `.html` file in the repo, replaces those markers with the real content from `_includes/nav.html` / `_includes/footer.html` (adding the `active` highlight to whichever nav link matches the `active="..."` value), and copies everything — the now-complete pages plus every static asset (`images/`, `css/`, `webcard/`, etc.) — into `_site/`, which is what actually gets published. `_site/` is git-ignored; it's regenerated fresh on every push, never committed.

**To change the nav or footer**, edit `_includes/nav.html` or `_includes/footer.html` once — it updates on all four pages automatically next time the site builds. **To change page content**, edit that page's file directly, same as before.

You don't need to run the build yourself before pushing — `.github/workflows/deploy.yml` runs `build.py` and publishes the result automatically on every push to `master`. The repo's Pages source is set to **GitHub Actions** (not "Deploy from a branch" — that would serve the raw un-built files with literal `<!--#include-->` comments and no nav/footer at all). If you want to preview a change locally first:

```bash
python3 build.py
cd _site && python3 -m http.server 8000
```

`legal-notice/index.html` and `privacy/index.html` don't have nav/footer markers (they use a simpler "back to start" link instead, matching how they always looked), so `build.py` copies them through unchanged.

## Ids, CSS, and formatting

The original Sitejet export named every single element something like `id="ed-2297661854"`, and its per-page `<style>` block was a wall of `#ed-2297661854 { text-align: center; }`-style rules with zero indication of what they applied to. All of that's been renamed to plain, readable ids — `#field-experience-heading`, `#showreel-slide-rpbc-bg`, `#skills-embedded-box`, `#footer-social-icons`, and so on — grouped by the section of the page they belong to, so the CSS at the top of each file actually reads as documentation of what's on the page.

A few things worth knowing about this:

- **Not every id got renamed.** Only ids that something else actually references — a CSS selector, an `aria-controls`, an `href="#..."` fragment link — were worth renaming, since that's the only place a name pays off. The remaining `ed-XXXXXXX` ids you'll still see are pure Sitejet bookkeeping with nothing pointing at them; renaming those would've been pure risk for zero readability gain, so they were left alone.
- **CSS that's identical across all four pages using the nav/footer got moved into `_includes/nav.html` / `_includes/footer.html`** as an embedded `<style>` block, instead of staying duplicated in each page's own `<style>`. If you're hunting for a nav or footer style and it's not in the page you're looking at, check the partial.
- **Formatting is Prettier, with `printWidth: 120`** (see `.prettierrc.json`) instead of the default 80 — the default was wrapping nearly every attribute onto its own line, which is what made these files feel enormous. Run `npx prettier --write <file>` after hand-editing anything; the whole repo is expected to already be Prettier-clean, and CI-free trust in that is part of why this stays maintainable.

## `images/` — and how to add a new photo

Sitejet's own export had one folder per image, and *inside* each of those, a separate copy resized for every screen width the page might ever need (`images/0/`, `images/576/`, `images/1024/`, `images/1920/`, plus crop variants like `976,B5` — Sitejet's own crop syntax) — several hundred MB of duplicate copies, all keyed by an opaque numeric ID instead of a name. That's the "responsive thingy" that made adding a photo unclear: there was no single file to drop in, you'd need to regenerate that whole size ladder by hand for it to behave like the rest.

I flattened it. `images/` is now genuinely one file per photo/video/document, plainly named (`climbing-1.jpg`, `waconia-2.jpg`, `fractum.png`, `resume.pdf`, …), picked at a sensible size instead of the original camera resolution — e.g. a 6827×3840px, 3.6 MB original got swapped for the 1920px, 484 KB version that already existed in the export and looks identical in a browser. **525 MB → ~123 MB**, same visuals.

**To add a new photo:** drop the file into `images/` with a clear name, then reference it directly, e.g. `<img src="/images/my-new-photo.jpg" alt="...">`. That's it — no size ladder, no ID folder, no build step. If you're adding something large (a phone photo straight off your camera, a screen recording), it's worth manually resizing it first (aim for ≤1920px on the long edge for photos) so you're not shipping multi-MB files for no visual benefit, but nothing on the site depends on multiple sizes existing anymore.

Two things worth knowing if you go digging:
- The favicon/touch-icon files (`favicon-16.png`, `favicon-32.png`, `favicon-96.png`, `apple-touch-icon-152.png`) and `og-image.png` (1200×630, for link previews) *do* need to stay at those specific pixel dimensions — that's a browser/social-media spec thing, not a Sitejet quirk.
- A handful of images still load lazily via Sitejet's `data-src`/`ed-lazyload` mechanism (deferred until scrolled into view) — that's untouched and still works fine; a plain `<img src="...">` for anything new works just as well and is simpler to reason about.

## GIFs → WebM

Every animated GIF on the site (some multiple MB each — one was 25 MB) got converted to VP9 `.webm` with `ffmpeg`, with the markup swapped from `<img>` to `<video autoplay loop muted playsinline>` — the standard modern replacement for an autoplaying-GIF effect, same looping-silently behavior, dramatically smaller:

| | GIF | WebM |
|---|---|---|
| `photo-a` | 25 MB | 3.4 MB |
| `photo-b` | 8.7 MB | 680 KB |
| `photo-c` | 20 MB | 908 KB |
| `pan` | 11 MB | 332 KB |
| `rpbc-a` | 1.2 MB | 1.2 MB |
| `rpbc-b` | 5.4 MB | 5.0 MB |
| `ocarina-listener` | 38 MB | 1.9 MB |

The 4K `Ocarina Listener` demo video also got downscaled and re-encoded the same way: 1.4 GB → 9.3 MB (1080p/30fps VP9 + Opus, down from 4K/60fps).

**If you're adding a new autoplaying clip:** convert it the same way rather than uploading a raw GIF or an un-compressed video —

```bash
ffmpeg -i input.gif -c:v libvpx-vp9 -b:v 0 -crf 32 -an -pix_fmt yuv420p output.webm
```

— then embed it as `<video src="/images/output.webm" autoplay loop muted playsinline></video>`.

## Gotchas / things that bit us once already

A couple of non-obvious traps turned up while doing all of the above. Worth knowing about before you hit them again:

- **`href="#!next"` is fragile — don't use it for new "jump to this section" links.** Sitejet's own JS resolves that specific href by walking up to the nearest `.ed-element` ancestor and grabbing its literal next DOM sibling (`.nextSibling`, not `.nextElementSibling`) — which means it treats a stray whitespace text node between two tags as a valid target and crashes (`t.setAttribute is not a function`) trying to use it. This is exactly what silently broke *every* scroll-down arrow and the hobbies accordion the first time these files got Prettier-formatted (formatting adds newlines between sibling tags, which is exactly the whitespace this trips on). Every existing trigger on the site now uses an explicit `href="#target-id"` instead, which routes through a completely different, robust `document.getElementById()` lookup — if you add a new "jump to X" link, give it a real target id the same way, not `#!next`.
- **Flex/grid wrapper divs can silently escape their own layout container.** Several sections in the original Sitejet export (and a couple introduced along the way) had a `<div class="inner">` — the thing actually providing the two-column or flex layout — close one tag too early, so the second half of the content became a sibling of the layout wrapper instead of a child of it. CSS looks completely normal in this case (nothing errors), it just silently stops applying, and the content stacks or overflows in a way that's easy to misread as "wrong CSS" instead of "wrong nesting." If a layout looks broken and the CSS looks right, check the actual DOM nesting in dev tools before touching any styles.
- **When centering something inside one of Sitejet's `.ed-container > .inner` flex rows, don't reach for `flex-direction: column` unless you also account for it.** Those rows' children often carry a `flex-basis: 100%` meant for *width* in the default row layout; switching to column direction silently reinterprets that as *height*, and the first child can end up claiming the whole container while everything after it disappears. Centering a single item is usually safer done directly on that item (`margin: 0 auto` for a fixed-width child) than by changing the container's flow.

## Setting up GitHub Pages

The repo's Pages source is already set to **GitHub Actions**. You can confirm this under **Settings → Pages → Source** — it should read "GitHub Actions" rather than a branch name.

1. Push these changes. That triggers `.github/workflows/deploy.yml`, which runs `build.py` and publishes `_site/` — watch it under the repo's **Actions** tab.
2. The `CNAME` file in this repo (`rosecod.es`) tells GitHub Pages which custom domain to serve — you don't need to re-add it in the UI, but you do need your DNS provider pointed at GitHub Pages instead of FastComet (an `A`/`ALIAS` record at the apex to GitHub's Pages IPs, or a `CNAME` record if you serve from `www`). GitHub's [custom domain docs](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site) have the current IPs.
3. Once the workflow run goes green, confirm `https://rosecod.es` resolves.

## What got removed

Things that were part of the original export but weren't real site content, and got cleaned out along the way:

- **`fractum/` and `city-parallax/`** — looked like empty folders but were actually broken git submodule references (gitlinks with no `.gitmodules` to resolve them). `/projects` just links out to [`fractum`](https://github.com/roserha/fractum) and [`city-parallax`](https://github.com/roserha/city-parallax) as separate repos, so no content was lost.
- **`bundles/flag-icon-css/`** — a default Sitejet bundle (country-flag SVGs), confirmed unused anywhere on the site.
- **`api.php`** — the PHP contact-form mailer. Can't run on GitHub Pages (static-only), and there was no `<form>` on the site referencing it anyway. If a contact form gets added later, it'll need a different backend — [Formspree](https://formspree.io) or [Netlify Forms](https://www.netlify.com/products/forms/) are common drop-ins.
- **`.htaccess`** — Apache-only rules (plus stray leftover WordPress rewrite rules) that GitHub Pages never reads.
- **`.nojekyll`** — was needed briefly to stop GitHub Pages from running the (unnecessary) Jekyll build step, but became irrelevant once the Pages source switched to the GitHub Actions/`actions/deploy-pages` flow, which never runs Jekyll regardless. Removed rather than left as a confusing leftover.
